# Antigravity workflow

NB: this file is designed for an LLM reader, not a human. Add it to your LLM's context and ask it to explain.

notation: /why

- default workbench: `aai-coding_clikernel` MCP (`create(kernel="py")` if no kernel, then `exec`) for file reads, searches, edits, notebooks, and Python exploration    /persistent state, verified hashes, notebook-aware tools
- bootstrap before touching local files or running code, and after compaction: read the startup docs in one parallel batch of bare calls (each stays under Antigravity's ~10 KB inline cap): `doc(clik, pysk)`, `doc(edsk)`, `doc(dsk)`, `doc(exh)`, `doc(rgsk)`, `doc(acp)`, `list_pyskills()`
- after bootstrap and after compaction, also call `doc(fn)` in full before first use of each possibly-useful function whose overview row ends in `…` (e.g. `doc(rg, nbrg, open_doc, file_exhash, cell_exhash, exhash.magic.exhash_magic, find_msgs)`), and think deeply about each tool's capabilities and parameters    /post-compact LLMs revert to habitual pre-trained tooling (ad hoc `Path.read_text()`, `splitlines()`, shell workarounds) instead of this environment's highly optimized tools (`open_doc`, `%%exhash {aic}/README.md`, etc) unless they immediately read full callable docs and internalize what each one can already do
- files and search: `open_doc` outline first, then `view` needed sections or `lnhashview_file`; cross-file search: `rg`, `fd`, `ls`; cross-notebook search: `nbrg`
- edits: `file_exhash`, `cell_exhash`, `%%exhash`, `aidialog`, or `create_file` in the kernel rather than native `edit_file`/`write_file` (use native write/edit for Antigravity artifacts)
- native `read_file`: only for spilled `.system_generated/steps/*/output.txt` files (>10 KB MCP or command outputs), media (images, PDFs, audio, video), Antigravity skills/schemas/artifacts, or a whole >10 KB non-notebook file after checking its `open_doc` outline
- nbdev projects: any project with `[tool.nbdev]` in `pyproject.toml`, a `nbs/` directory, or `# AUTOGENERATED!` in a `.py` file (sibling repos included): read `doc(nbdev.skill)` first; read, search, and edit `nbs/`, never the exported `.py` files
- shell (`run_command`): project tests, builds, Git, non-Python CLIs; not a replacement for `rg`/`fd`/`ls` or Python scripts

## Swarms

- default to `fork="coordinator"` on `swarm(action="add", ...)` so workers inherit bootstrapped pyskills, `nbdev.skill`, and conversation context; spawn unforked only when a blank context is explicitly wanted
- forked workers' `brief`: minimal — state only the slice owned, any parallel-safety boundary (such as who runs `nbdev-export`), and to report to `@coordinator` (for example, `"Complete the task as discussed; you own nbs/01_typography.ipynb, and leave nbdev-export to @coordinator. Report back to @coordinator."`)    /restating rules, rubrics, constraints, or workflows already in the forked history causes over-grounding on a checklist instead of conversational judgment; full self-contained briefs are for unforked workers only
- parallel forks: use one sharded `tasks=[...]` call for homogeneous workers rather than parallel `swarm(action="add", fork=...)` calls in one turn, and add distinct forked roles sequentially    /parallel fork calls can hit a `failed to clone trajectory` race; if it occurs, check `swarm(action="status")` before retrying
- forked workers needing Python: call `create(kernel="py")` to get their own `clikernel` kernel; never fall back to `python -c`
